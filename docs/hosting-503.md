# Diagnóstico de SERVICE_UNAVAILABLE en Hostinger

## Evidencia y límites (27 de octubre de 2026)

Se revisó el PR #5, `codex/security-hardening`, cuya cabeza era `38a754a0efb88206bd001042d02ac572a3768eeb`; main seguía siendo el README inicial. No se presupone que la instalación corresponda a esa cabeza. Los GET de `/v1/health`, `/v1/public/motorcycles`, `/v1/public/promotions` y OPTIONS de `/v1/public/leads` devolvieron 503 con `SERVICE_UNAVAILABLE` y sin Access-Control-Allow-Origin. Referencias de esa comprobación: `506470056dbb6482d93b0bc5`, `9c1b99efb5dd889f40f2352b`, `f8509c0e0ec2a4fb3c459907`, `cda78931c47c5a1628fef776`. También se recibieron del operador las referencias `d6bdcd66a24966bbb89bfe2b` y `3341dc3674822b865b24999b`.

En la revisión examinada ese mensaje se emite exclusivamente al fallar `requireSecureRuntime()`, antes de health, autenticación y cualquier consulta MySQL. El guard exige PHP 8.3.36+, 8.4.27+ o 8.5.12+, `pdo_mysql` y `sodium`. La ausencia de CORS se explica por ejecutar el guard antes del bloque CORS. MySQL, SMTP, claves MFA y migraciones no son comprobados por ese guard y no explican por sí mismos este mensaje concreto.

El log anterior no distinguía cuál condición falló. No hay acceso administrativo a Hostinger, sus logs privados, PHP web, permisos efectivos, OPcache o archivos instalados. Por ello **no se ha identificado aún cuál requisito concreto falla ni el SHA realmente instalado**. Las respuestas son compatibles con ese guard, pero no permiten certificar que todo el paquete esté actualizado. Una cabecera PHP anterior, `php -v` o un CI exitoso no prueban la configuración web actual.

## Corrección de aplicación

- Configura CORS antes del guard, únicamente para los orígenes de `allowed_origins`. Una respuesta 503 mantiene el mismo error genérico y X-Request-ID, con cabeceras CORS para el origen permitido. Un origen rechazado recibe 403 sin reflejarlo; no se añade wildcard. OPTIONS sigue rechazando un runtime inseguro con 503 en vez de simular salud.
- Al rechazar el runtime registra **solo en el log privado** un evento JSON `runtime_unavailable`, con requestId, versión/ID PHP, SAPI, booleanos de extensiones, motivos `php_version`/`pdo_mysql`/`sodium`, estado básico de OPcache y hashes de archivos en disco. No incluye configuración, rutas absolutas, credenciales, trazas, correos ni tokens. El cliente no recibe este diagnóstico.
- Los paquetes nuevos incluyen hashes SHA-256 en el manifiesto privado y un comprobador CLI de solo lectura, `bin/check-installation.php`. Detecta archivos faltantes o distintos; no consulta MySQL, ejecuta migraciones ni envía SMTP. Un paquete antiguo sin hashes queda como no verificable, no como correcto.
- No se bajan los mínimos PHP ni se deshabilitan comprobaciones. No hay bypass mediante variables, cabeceras o parámetros del visitante, ni endpoint phpinfo/OPcache.

## Intervención exacta en Hostinger

1. En hPanel abre **Sitios web → panel del sitio de la API → Configuración PHP**. Comprueba la versión del PHP que atiende ese dominio y sus extensiones. Selecciona una rama admitida cuyo parche real cumpla el mínimo, y habilita `pdo_mysql` y `sodium` en ese PHP. El selector elige la rama; Hostinger administra el parche. Si una extensión o parche requerido no está disponible, solicita su instalación a soporte. No inventes una directiva extension= en .htaccess ni bajes el guard.
2. Para confirmar el PHP **web**, usa información privada de PHP en hPanel o el evento `runtime_unavailable` de una solicitud tras instalar esta corrección de forma autorizada. Lee `failures`: `php_version` requiere actualizar el runtime web; `pdo_mysql` o `sodium` requieren habilitar esa extensión en ese SAPI. Puede haber más de un fallo. No publiques phpinfo ni compartas el contenido completo de la configuración.
3. Hostinger documenta mitigaciones del proveedor contra PHP2Shell. Eso no prueba el parche numérico de esta cuenta. Si soporte afirma que es un backport con número inferior, pide identificación del paquete y evidencia del parche; requiere una evaluación específica, no una excepción automática ni una declaración del cliente.
4. Comprueba privadamente `deployment-manifest.json` en la carpeta **superior a public_html**, su `sourceRevision` y que esa sea la cuenta/directorio del dominio API. Para un paquete nuevo ejecuta allí `php bin/check-installation.php` con una ruta PHP conocida. El resultado identifica el **CLI**, no el PHP web. No subas el manifiesto, src, config, bin o vendor al directorio público. Conserva config.local.php y claves existentes.
5. Si hay archivos mezclados, prepara el paquete completo de una única revisión, respalda y reemplaza los archivos de aplicación en una ventana autorizada siguiendo hosting-403.md. No repares solo index.php dejando runtime.php viejo. Compara hashes del manifiesto entregado; los hashes del log describen el disco, no certifican el bytecode en memoria. El manifiesto tampoco sustituye el checksum de la entrega de confianza.
6. Tras cualquier cambio de versión/extensiones o reemplazo autorizado, solicita reiniciar los trabajadores PHP **web** y limpiar su OPcache mediante los controles del proveedor o soporte. Un `opcache_reset()` desde CLI no acredita que el proceso web haya sido renovado. Purgar CDN tampoco reinicia OPcache. No publiques un script de reset ni desactives OPcache globalmente como solución.
7. Repite solo GET de health/catálogo/promociones y OPTIONS con `Origin: https://wheat-stinkbug-153908.hostingersite.com`. Esperado, una vez corregido el runtime: health 200 `{data:{status:"ok"}}`, catálogo/promociones 200 con data array, OPTIONS 204, X-Request-ID y CORS del origen exacto. Vacío es válido; no reemplazar errores por ejemplos. Si después aparece un error DB distinto, investiga ese nuevo error con su requestId privado; no reimportes schema.sql.
8. Verifica por separado PHP CLI del cron, migraciones pendientes y worker según security-hardening.md. No son prueba ni corrección del PHP web y este cambio no requiere una migración nueva.

Referencias oficiales: [versión PHP en Hostinger](https://www.hostinger.com/support/1575755-how-to-change-the-php-version-of-your-hostinger-hosting-plan/), [extensiones PHP](https://www.hostinger.com/support/which-php-extensions-and-configuration-options-are-supported-at-hostinger/), [protecciones PHP2Shell](https://www.hostinger.com/blog/protecting-php2shell/), [opcache_reset](https://www.php.net/manual/en/function.opcache-reset.php).

## Pruebas aisladas

CI conserva health/catálogo/promociones con PHP admitido y MySQL desechable. `tests/runtime.php` clasifica por separado versión, cada extensión y fallos combinados. `tests/runtime_http.py` inicia otro PHP web local con `-n` y sin PDO MySQL, verifica el rechazo real de GET/OPTIONS antes de consultar DB, CORS permitido/denegado/ausente, error genérico y motivos en log privado. El guard no recibe opciones para simular o saltar requisitos en producción. `tests/install_check.py` detecta mezcla de archivos y manifiesto ausente en una extracción aislada. Ninguna prueba despliega o usa correos/leads reales.
